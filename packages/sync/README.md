# bloom-sync

Platform-neutral sync and end-to-end encryption core for Bloom. TypeScript, ESM, WebCrypto only (no third-party crypto).
It builds to `web/bloom-sync.js` (IIFE, `window.BloomSync`) for the web app and is imported directly by the React Native app.

```sh
npm install
npm test            # vitest, coverage gate >= 85%
npm run build       # -> ../../web/bloom-sync.js (minified)
npm run seal        # rewrites the Content-Security-Policy <meta> in web/index.html (hashes + sync origin)
```

## Injected dependencies (`createSync(deps, options)`)

`storage` (async key/value; web: localStorage), `fetch`, `crypto` (`subtle` + `getRandomValues`), `clock`
(`now`, `setTimeout`, `setInterval`, clears), `lifecycle` (visibility, online, hide), optional `keyStore`
(device store for the data key), `emit` (events to the UI), `abort`. The core touches no globals; `src/web-platform.ts`
and `src/browser.ts` are the only browser glue. Tests use a fake clock, in-memory storage and an in-memory server.

## Keys and formats (all versioned)

| Item | Definition |
| --- | --- |
| masterKey | PBKDF2-SHA256(password NFKC, salt = `"bloom-kdf-v1|" + email(NFKC, trimmed, lowercase) + "|" + kdfSalt`, >= 600,000 iterations, 256 bits). `kdfSalt` is 16 random bytes generated by the client and stored by the server with the iteration count; `GET`/`POST /v1/auth/prelogin` returns them. The client refuses fewer rounds than its floor, so a hostile server cannot downgrade it. |
| authKey | HKDF-SHA256(masterKey, info `bloom/auth/v1`), 256 bits. Sent instead of the password. The server hashes it again (PBKDF2, 100k, its own salt). |
| kek | HKDF-SHA256(masterKey, info `bloom/kek/v1`) as a non-extractable AES-256-GCM key. Never leaves the device. |
| DEK | 256 random bits. Encrypts all data. In memory (and optionally IndexedDB) as a non-extractable `CryptoKey`. |
| wrappedDek | `{v:1, iv, ct}` = AES-256-GCM(kek, DEK), AAD `bloom|dek|v1` |
| recovery key | 256 random bits + 24-bit checksum, shown once as 14 groups of 4 base32 characters. |
| recoveryAuth, recoveryKek | HKDF of the recovery key, infos `bloom/recovery-auth/v1`, `bloom/recovery-kek/v1`. The server stores a hash of recoveryAuth. |
| recoveryWrappedDek | AES-256-GCM(recoveryKek, DEK), AAD `bloom|dek-recovery|v1` |
| document | `{v:1, iv, ct}`: AES-256-GCM, random 96-bit IV, 128-bit tag, AAD `userId|collection|docId|v1`, plaintext = JSON body (+ merge metadata) |
| shot | bytes `"BSE\x01" | iv(12) | ct+tag`, AAD `userId|shots/machineId|shotId|v1`. No metadata is sent. |

`v` selects the algorithm set, so a new cipher or KDF is a new version that old and new clients can tell apart.

## Flows

* **signup**: derive keys, generate DEK + recovery key, send `authKey`, kdf, `wrappedDek`, `recoveryWrappedDek`, `recoveryAuth`.
  `auth.signup()` returns `{id, email, name, recoveryKey}`; the key is not kept anywhere.
* **login**: prelogin, derive, send `authKey`, unwrap `wrappedDek` from the response. A key that does not open means the server is lying: the new session is revoked.
* **stay signed in** (default): the DEK is saved via `keyStore` (web: non-extractable CryptoKey in IndexedDB). Without it a reload leaves the session **locked** until `auth.unlock(password)`.
* **recover**: `recoveryAuth` proves possession, the server returns `recoveryWrappedDek`, the client unwraps it, chooses new kdf params + password, re-wraps, uploads. All old sessions are revoked.
* **change password**: unwrap with the current password (checked locally and by the server), re-wrap with the new one; other sessions are signed out. The DEK itself does not change (so the recovery key stays valid).

## Conflict resolution (field level)

Each document body holds `_m: { field: [hlc, deviceId] }` (and `_del: [hlc, deviceId]` once deleted) inside the encrypted payload.
`hlc` is a hybrid logical clock string `wallMs(15 digits).counter(hex5)`: monotonic per device and advanced on every document received, so a
slow clock cannot lose forever (a remote stamp more than 24 h in the future is ignored for the clock). Stamps compare by `hlc`, then `deviceId`.

* A field is a last-writer-wins register; the higher stamp wins. Arrays and nested objects are one field.
* `set(obj)` stamps every field in `obj` and writes a *field tombstone* (stamp, no value) for known fields it omits.
* `update(obj)` stamps only the given fields. `delete()` stamps the document-level `_del`.
* A document delete hides every field stamped before it and loses to any field written after it (that field alone comes back).
* Bodies without `_m` (older clients) count as stamp `0` everywhere, so any stamped edit beats them.
* `mergeStates(a, b)` (src/merge.ts) is pure, commutative, associative and idempotent (property tests: random interleavings over 2-3 devices with skewed clocks converge).
* When the server rejects a write with `409 conflict` (stale `baseSeq`, below) the client fetches and decrypts the latest copy, merges the queued op into it
  field by field, and retries (up to 5 times, then the op stays queued). A pulled server copy never replaces pending local edits: snapshots are the server copy with
  queued ops merged over it. `_m` / `_del` are stripped before data reaches Bloom and kept on every write; values hidden by a delete are dropped from the payload.

Writes are `PUT /v1/docs/:c/:id?baseSeq=N`: the server only accepts it if the live document still has seq `N` (0 = must not exist), atomically.
There is no server-side merge and no `PATCH` (the server cannot read the data). Deletes are written as encrypted tombstones, so a stale device cannot undelete.

## Integrity and races

A document that fails authentication (tampered ciphertext, wrong AAD such as a document moved to another id or account, wrong key) is skipped: the cached copy is
untouched, the status becomes `error: integrity`, and the rest of the page still applies. Network errors never touch the cache. Flushing and pulling are
single-flight (a pull requested mid-pull gets one trailing pass); a generation counter makes any response from before a logout / re-login a no-op; snapshots are built
from the latest state at delivery time, so they are ordered.

## Threat model

Protects against: a server, database leak or backup reader, or network observer learning document or shot contents, the password, or any key.
The server cannot forge or move your data undetected (AAD binds user, collection and id).

Not protected / still visible to the server: email (and display name if sent; Bloom sends none), account creation time, KDF parameters, collection names and document ids
(e.g. `brews/b1…`, which embed a timestamp), approximate document sizes, shot ids and byte sizes, write counts and timing, IP addresses. A malicious *server* could
withhold or roll back documents (it cannot alter them), or serve a client-side attacker's JavaScript if the web host itself is compromised (E2E cannot protect a
user from code the same origin ships). A weak password can be guessed offline by anyone who steals the database (600k PBKDF2 slows this; it does not stop it);
the recovery key is the strongest secret, store it offline. On the device, the cache and queue are stored as plaintext in localStorage, exactly like Bloom's own local
data; the DEK in IndexedDB is non-extractable, but script running in the page can still *use* it, and clearing site data or logging out removes it.
